# PRD · Модуль «AI-шар»

**Статус:** до розробки · **Версія:** 1.0 · **Залежності:** `docs/db/schema.dbml` (`embedding`, `ai_task`), `docs/api/openapi.yaml` (тег `Search`, ендпоінт `/search/semantic`)

## 1. Мета і межі модуля

AI прискорює каталогізацію і пошук, **ніколи не публікує факти без людини**. Кожен AI-вихід — чернетка зі статусом `requires_human_review`. Технологічний вибір ґрунтується на дослідженні ринку 2025–2026: **Transkribus/eScriptorium** для HTR рукописного тексту, мультимодальні embeddings (CLIP-подібні) + self-hosted векторна БД (pgvector → Qdrant) для семантичного пошуку без вендор-лока.

## 2. User stories

| # | Роль | Історія |
|---|------|---------|
| AI1 | Архіваріус | Хочу отримати чорновий опис і теги для щойно завантаженого фото, щоб не писати з нуля |
| AI2 | Дослідник | Хочу знайти документи за змістом, а не лише точним збігом слів |
| AI3 | Модератор | Хочу, щоб токсичні/спам-коментарі автоматично піднімались у черзі для першочергового розгляду |
| AI4 | Родич рукописного листа | Хочу отримати розпізнаний текст листа з фронту, написаного від руки |
| AI5 | Іноземний дослідник | Хочу прочитати картку захисника англійською через авто-переклад |
| AI6 | Куратор музею | Хочу отримати підказку про тематично повʼязані експонати (за прикладом Art Aura від Google/Met) |

## 3. Функціональні вимоги — по можливостях

| Можливість | Модель/підхід | Вхід → вихід | Роль людини |
|---|---|---|---|
| Авто-опис медіа | Мультимодальна VLM (напр. відкрита модель класу LLaVA/Qwen-VL, self-hosted або через контрольований API) | зображення → `title`/`description`-чернетка + теги | Архіваріус підтверджує перед публікацією |
| OCR друкованого тексту | Tesseract 5 + мовна модель постобробки для виправлення розпізнавання | скан → `ocr_text` + координати слів | Вичитка архіваріусом для критичних документів |
| HTR рукописного тексту | Transkribus API (готові моделі під історичні почерки) або self-hosted eScriptorium | скан рукопису → текст | Обов'язкова вичитка (точність HTR нижча за друкований OCR) |
| Семантичний пошук | Текстові embeddings → `pgvector`, HNSW-індекс; масштабування на Qdrant при рості обсягу | запит → ранжований список сутностей | — (допоміжний UX, не факт) |
| Пошук за зображенням / подібністю | CLIP-подібні мультимодальні embeddings | зображення → схожі зображення/предмети | Модерація неоднозначних збігів (особливо для облич) |
| Рекомендації «повʼязане» | Комбінація графу (спільний підрозділ/місце/дата) + векторна подібність | сутність → список повʼязаних | — |
| Переклад | LLM-переклад укр↔англ карток і статей | текст → переклад-чернетка | Редактор перевіряє ключові публічні тексти перед публікацією |
| Авто-модерація UGC | Класифікатор токсичності/спаму/PII (fine-tuned або prompted LLM) | текст спогаду → прапорці `ai_flags` | Модератор приймає остаточне рішення завжди |
| Чат-помічник (RAG) | LLM + retrieval виключно по `status = published` контенту платформи, з обовʼязковим цитуванням джерела | запитання → відповідь з посиланнями на PID | Тільки verified-корпус; відповіді без джерела блокуються |
| Голосовий пошук | STT (Whisper-подібна модель) | аудіо → текстовий запит | — |

### 3.1 Черга AI-задач

- Кожна AI-операція — запис в `ai_task` (`task_type`, `status`, `result`, `confidence`, `requires_human_review`).
- Задачі виконуються асинхронним воркером (RabbitMQ consumer), не блокують основний запит користувача.
- Низька `confidence` (нижче конфігурованого порогу) автоматично підвищує пріоритет ручної перевірки в черзі модерації.

### 3.2 Семантичний пошук — деталі

- `embedding.entity_type` покриває `defender`, `media`, `story`, `exhibit` — окремий embedding на сутність, перерахунок при суттєвій зміні тексту (тригер по `content_revision`).
- `GET /search/semantic` повертає `SemanticSearchHit[]` з `score`; UI показує як доповнення до звичайного пошуку («Можливо, ви шукали...»), не замінює точний повнотекстовий пошук.

### 3.3 Розпізнавання облич — етичні обмеження

- Використовується **виключно** для звʼязування вже завантажених родиною фотографій одного захисника між собою (кластеризація фото в межах його ж профілю), **не** для ідентифікації особи серед сторонніх фото і **не** для живих людей.
- Явна згода (`consent_record.consent_type = 'process_pii'`) обовʼязкова перед активацією для конкретного профілю.
- Жодної біометричної бази для розпізнавання «хто це» серед незвʼязаних фото.

### 3.4 Чат-помічник — гардрейли

- RAG виключно по контенту зі статусом `published` і `verification_status IN ('verified','pending')` — ніколи по чернетках чи неопублікованому.
- Кожна відповідь містить список використаних джерел (PID профілів/документів); відповідь без можливості процитувати джерело не видається користувачу, а замінюється на «Не маю підтвердженої інформації з цього питання».
- Заборонено генерувати біографічні факти, яких немає в базі («заповнення прогалин» текстом моделі) — тільки перефразування наявних верифікованих даних.

## 4. Продуктивність і масштаб

- OCR/HTR-черга — найважча за обчисленнями; окремий пул воркерів, що масштабується незалежно (`ai-worker` сервіс, винесений з монолітного ядра — див. Backend Architecture).
- Embedding-модель для семантичного пошуку — досить лаконічна для CPU-інференсу на MVP-масштабі; GPU-інференс — рішення для Фази 2.0 при рості обсягу колекцій.

## 5. Дані і API (посилання)

- Схема: `embedding` (pgvector, HNSW-індекс), `ai_task`.
- Ендпоінти: `GET /search/semantic`; авто-опис/OCR — внутрішні воркер-процеси, не мають публічного REST-виклику (запускаються автоматично конвеєром ingest, див. PRD 04 Archive).

## 6. Метрики успіху

- Частка AI-чернеток (опис/теги), прийнятих архіваріусом без правок — індикатор якості моделі (ціль ≥60% на старті, зростання з часом).
- Латентність семантичного пошуку — &lt;500ms p95.
- 0 випадків публікації AI-згенерованого «факту» без верифікації людиною (аудиторська перевірка щомісяця).

## 7. Ризики

- **Галюцинації LLM** у чат-помічнику — мітигується жорстким RAG-обмеженням і обов'язковим цитуванням; regression-тести на «відмову відповідати» за межами корпусу обовʼязкові в CI.
- **Якість HTR на історичних почерках** різна — потрібне пілотне тестування на реальних листах з архіву регіону перед вибором конкретної моделі/провайдера.
- **Вартість inference** при масштабуванні на національний рівень — закладати self-hosted опції (eScriptorium, відкриті embedding-моделі) як стратегію зниження залежності від платних API.
