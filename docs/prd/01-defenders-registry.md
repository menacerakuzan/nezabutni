# PRD · Модуль «Реєстр захисників»

**Статус:** до розробки · **Версія:** 1.0 · **Залежності:** [`docs/db/schema.dbml`](../db/schema.dbml) (таблиці `defender`, `unit`, `defender_award`, `defender_place_role`, `defender_relation`, `defender_submission`, `consent_record`), [`docs/api/openapi.yaml`](../api/openapi.yaml) (теги `Defenders`, `UGC`)

## 1. Мета і межі модуля

Реєстр — центральний домен платформи. Кожен інший модуль (карта, музей, архів) посилається на `defender` як на канонічну сутність людини. Модуль відповідає за:

- створення, редагування та публікацію профілю захисника;
- дворівневу модель довіри: **офіційна верифікація** (ВА/ТЦК) окремо від **народного шару памʼяті** (UGC-спогади, свічки);
- процес подання інформації родиною через майстер із 5 кроків;
- зв'язки людини з підрозділом, місцями, нагородами, іншими людьми.

**Не входить у цей модуль** (див. відповідні PRD): зберігання самих медіафайлів (→ Archive), картографічне відображення (→ Map), музейні експозиції (→ Museum), сам процес модерації черги (→ CMS).

## 2. User stories

| # | Роль | Історія | Критерій готовності |
|---|------|---------|----------------------|
| U1 | Громадянин | Як відвідувач, я хочу знайти профіль за іменем за &lt;2с, щоб вшанувати память | Пошук `full_name_normalized` через `pg_trgm`, p95 &lt;300ms на бекенді |
| U2 | Родич | Як сестра загиблого, я хочу подати заявку на створення профілю з фото і документами | Форма-майстер `POST /submissions`, статус `pending` видно в кабінеті |
| U3 | Родич-«хранитель» | Як власник профілю, я хочу редагувати біографію після підтвердження | `guardian_user_id` дає право `PATCH /defenders/{pid}` без ролі editor |
| U4 | Верифікатор (ВА/ТЦК) | Як верифікатор, я хочу порівняти заявку з офіційними даними і затвердити/відхилити | Окрема черга `assigned_verifier_id`, рішення логується в `audit_log` |
| U5 | Дослідник | Як історик, я хочу відфільтрувати захисників за підрозділом і періодом і експортувати список | `GET /defenders?unit_id=&death_date_from=` + `GET /export` |
| U6 | Побратим | Як ветеран, я хочу додати звʼязок «побратим» між двома профілями | `defender_relation`, потребує модерації як UGC |
| U7 | Гість | Як анонімний відвідувач, я хочу «запалити свічку» без реєстрації | `POST /defenders/{pid}/candles` за session fingerprint, rate-limit 1/добу |

## 3. Функціональні вимоги

### 3.1 Профіль захисника

- Обовʼязкові поля при публікації: `full_name`, хоча б одна дата (`birth_date` або `death_date`), `verification_status`.
- `pid` генерується автоматично за схемою `MEM-{рік створення}-{6-значний лічильник}`, незмінний після публікації.
- `bio_blocks` — блочний JSON (текст/цитата/фото-вставка) для багатого життєпису, редагується в блоковому редакторі CMS.
- Автоматичне обчислення `full_name_normalized` тригером БД (нижній регістр, транслітерація, без діакритики) — використовується для fuzzy-пошуку.
- CHECK-обмеження: `death_date >= birth_date`, якщо обидві дати задані.

### 3.2 Верифікація

Статуси `verification_status`: `draft → pending → verified | disputed → archived`.

1. Профіль створений editor'ом або через `defender_submission` → `draft`/`pending`.
2. Верифікатор із роллю `verifier_gov` звіряє з офіційними реєстрами (зовнішня інтеграція — поза MVP, вручну на старті).
3. Рішення `verified` фіксує `verified_by`, `verified_at`; рішення `disputed` вимагає `decision_note` з описом розбіжності і не блокує публікацію чернетки, але позначає банер «дані уточнюються» на публічній сторінці.
4. Будь-яка подальша правка верифікованого профілю створює `content_revision`, потребує повторного review, якщо зачіпає ключові факти (дати, місце, підрозділ) — визначається списком «критичних полів» у конфігурації.

### 3.3 «Хранитель профілю»

- Призначається автоматично заявнику (`submitted_by`) після затвердження заявки, якщо профіль новий.
- Може бути переданий іншому члену родини через запит у кабінеті + підтвердження модератором (запобігання захопленню профілю).
- Права хранителя: редагувати `bio`, завантажувати медіа, схвалювати/приховувати UGC-спогади на «своєму» профілі (але не остаточне видалення — це роль модератора).

### 3.4 Майстер подання заявки (5 кроків)

1. **Особа** — ПІБ, дати, місце народження.
2. **Служба** — підрозділ (автокомпліт по `unit`), звання, нагороди.
3. **Документи** — завантаження підтверджуючих файлів (посвідчення, витяг) → `attached_media_ids`.
4. **Медіа** — портрет, фотогалерея.
5. **Згода** — окремі чекбокси `publish_data`, `publish_media`, `process_pii` → записуються в `consent_record`, юридично обов'язкові, без них заявка не приймається.

Автозбереження чернетки заявки на кожному кроці (localStorage + періодичний `PATCH` за наявності сесії).

### 3.5 Свічки та вшанування

- Дедуплікація: одна свічка на профіль на добу для одного `user_id` **або** `session_fingerprint` (для анонімних).
- `candle_count` на `defender` — денормалізований лічильник, оновлюється асинхронно через чергу (не блокує запит).
- «В цей день вшановуємо» на головній — вибірка за `date_part('month', death_date) = today.month AND date_part('day', death_date) = today.day`, ротація серед кандидатів.

### 3.6 Звʼязки

- `defender_place_role` — рольовий звʼязок з місцем (`served_at|fought_at|died_at|buried_at|born_at`), живить таб «Карта шляху» на профілі і шар на глобальній карті.
- `defender_relation` — симетричний звʼязок «побратими»; додавання одним боком створює запис зі статусом `pending`, підтвердження другою стороною (якщо є профіль-хранитель) або модератором активує звʼязок.

## 4. UX і стани

- **Порожній стан пошуку:** «Профіль не знайдено» → CTA «Пропонуємо додати» веде прямо на крок 1 майстра з передзаповненим ПІБ.
- **Банер розбіжності** (`disputed`) на публічній сторінці: нейтральний тон, без згадки деталей спору, посилання «Повідомити про уточнення».
- **Приватність під час pending:** заявки на новий профіль не публічні, доки не пройде модерацію — уникаємо публікації неперевірених фактів про загиблого.
- Доступність: усі інтерактивні елементи мають фокус-стан, форма майстра повністю керована з клавіатури, помилки валідації прив'язані до полів через `aria-describedby`.

## 5. Дані і API (посилання)

- Схема: `defender`, `unit`, `defender_award`, `defender_place_role`, `defender_relation`, `defender_submission`, `consent_record`, `content_revision` — див. `schema.dbml`.
- Ендпоінти: `GET/POST /defenders`, `GET/PATCH /defenders/{pid}`, `GET /defenders/{pid}/timeline`, `POST /defenders/{pid}/candles`, `GET/POST /defenders/{pid}/memories`, `POST /submissions`.

## 6. Метрики успіху

- Частка профілів зі статусом `verified` серед усіх опублікованих — ціль ≥90% через 12 міс.
- Медіанний час від подання заявки до рішення верифікатора — ціль ≤5 робочих днів.
- P95 латентність пошуку за іменем — &lt;300ms.

## 7. Ризики та відкриті питання

- **Юридичний ризик:** потрібне узгодження з ДПА (Уповноважений з захисту персональних даних) щодо обробки даних про загиблих родичами, які не є прямими спадкоємцями.
- **Конфлікт даних:** два різні заявники подають суперечливу інформацію про одну людину — потрібен UI для верифікатора порівняння версій (side-by-side diff з `content_revision`).
- **Дедуплікація при імпорті** з Книги памʼяті / Мартирологу (згадано в дослідженні) — потрібен окремий batch-процес зіставлення за ПІБ+датами перед масовим імпортом, не входить у MVP.
