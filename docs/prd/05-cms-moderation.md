# PRD · Модуль «CMS і модерація»

**Статус:** до розробки · **Версія:** 1.0 · **Залежності:** `docs/db/schema.dbml` (`content_revision`, `defender_submission`, `memory_ugc`, `role`, `user_role`, `audit_log`), `docs/api/openapi.yaml` (тег `Moderation`)

## 1. Мета і межі модуля

Редакційне середовище рівня Notion/Linear поверх усіх контентних доменів (реєстр, музей, архів, карта): чернетки, workflow публікації, ролі, історія змін і єдина черга модерації UGC та заявок. Це не окремий домен даних, а **операційний шар** над сутностями інших модулів.

## 2. User stories

| # | Роль | Історія |
|---|------|---------|
| C1 | Контент-менеджер | Хочу зібрати профіль/експозицію з блоків і відправити на рецензію |
| C2 | Модератор | Хочу бачити єдину чергу всіх UGC-обʼєктів, що очікують рішення, з пріоритезацією |
| C3 | Верифікатор (ВА/ТЦК) | Хочу окремий потік заявок на верифікацію профілів, відмінний від загальної модерації |
| C4 | Адміністратор | Хочу бачити повний аудит-лог дій будь-якого користувача |
| C5 | Редактор | Хочу відкотити помилкову правку до попередньої версії |
| C6 | Контент-менеджер | Хочу запланувати публікацію статті на конкретну памʼятну дату |

## 3. Функціональні вимоги

### 3.1 Блоковий редактор

- Єдиний компонент для `defender.bio_blocks`, `exhibit.blocks`, `story.blocks` — типи блоків: `text`, `media`, `quote`, `model3d`, `panorama`, `map_embed`, `timeline_embed`.
- Кожен медіа-блок обирає файл з архіву через вбудований пошук (не завантажує повторно) — форсує повторне використання і єдину систему прав.
- Autosave кожні 10с чернетки в `content_revision` без створення видимої версії (лише при явному «Зберегти» створюється точка історії).

### 3.2 Workflow станів

`draft → in_review → published` (+ `archived` для зняття з публікації без видалення).

- Перехід `draft → in_review`: доступний editor, сповіщає призначеного рецензента.
- Перехід `in_review → published`: доступний ролям `moderator`/`admin`, або автоматично для `editor` з довірою (конфігурований поріг ролі — не в MVP).
- `published → archived`: доступний `admin`, обов'язковий коментар причини (юридичний запит, помилка, застарілість).

### 3.3 Єдина черга модерації

`GET /moderation/queue` обʼєднує три джерела: `memory_ugc` (spogady), `defender_submission` (заявки на профілі), `content_revision` для критичних полів верифікованих профілів (див. PRD 01, п.3.2).

- Пріоритезація: AI-прапорці (`ai_flags` — токсичність, PII, спам, дублікат) піднімають запис угору черги для модератора, **не приймають рішення самостійно**.
- Групові дії (batch approve/reject) для однотипних низькоризикових обʼєктів (напр. свічки не в черзі — вони не модеруються, лише rate-limited).
- Кожне рішення (`POST /moderation/queue/{id}/decision`) обов'язково пише `audit_log` з `diff` і, для відхилень, `rejection_reason`, видимою заявнику.

### 3.4 Верифікаційний потік (окремий від загальної модерації)

- Роль `verifier_gov` бачить лише `defender_submission` і критичні правки верифікованих профілів — не має доступу до UGC-модерації (розділення обов'язків).
- Може запросити додатковий документ у заявника через коментар до заявки (статус `pending`, заявник отримує сповіщення).

### 3.5 Версії і відкат

- Кожна опублікована зміна — запис `content_revision` з `diff` (JSON Patch) і, періодично (кожні 20 версій або раз на місяць), повний `full_snapshot` для швидкого відновлення без реплею всього ланцюга патчів.
- UI історії: список версій з автором, датою, коментарем; перегляд diff «до/після»; кнопка «Відновити цю версію» створює нову версію-копію (не видаляє історію).

### 3.6 Планування публікації

- Поле `published_at` у майбутньому + фонова задача (cron), що переводить `in_review → published` у заданий момент — для приурочення до памʼятних дат.

### 3.7 RBAC у CMS

Ролі з `role`/`user_role` (див. схему): `viewer`, `editor`, `moderator`, `archivist`, `verifier_gov`, `partner_curator`, `admin`, `superadmin`. Область дії (`scope_type`/`scope_id`) дозволяє обмежити роль конкретним регіоном або партнером — важливо для мультирегіонального масштабування (Roadmap 2.0+).

### 3.8 Аудит

- `audit_log` — тільки `INSERT`, партиціонований по місяцях, ніколи не редагується і не видаляється (навіть адміністратором) — гарантія розслідування інцидентів.
- Публічний (для admin/superadmin) перегляд з фільтрами за актором/сутністю/періодом.

## 4. UX

- Дашборд модератора: лічильники по типах черги, SLA-таймер (скільки обʼєкт чекає), клавіатурні шорткати approve/reject для швидкої обробки великих обсягів.
- Порожній стан черги — позитивне підтвердження «Черга порожня», а не мовчазна пустота.
- Diff-перегляд версій — side-by-side, зміни виділені кольором (додано/видалено/змінено), доступний з клавіатури.

## 5. Дані і API (посилання)

- Схема: `content_revision`, `defender_submission`, `memory_ugc`, `role`, `user_role`, `audit_log`.
- Ендпоінти: `GET /moderation/queue`, `POST /moderation/queue/{id}/decision`.

## 6. Метрики успіху

- Медіанний час обробки елемента черги — ціль &lt;48 годин для UGC, &lt;5 робочих днів для верифікації профілю.
- 0 випадків втрати історії версій (перевіряється тестами відновлення).
- 100% модераторських рішень мають запис в `audit_log` (перевіряється інваріантом на рівні транзакції).

## 7. Ризики

- **Перевантаження черги** при масовому імпорті (напр. дедуплікація з Книги памʼяті) — потрібен окремий batch-режим модерації з груповими діями, інакше черга стає непрохідною.
- **Розмежування ролей verifier_gov / moderator** критичне юридично — помилкове злиття прав може призвести до неавторизованої «державної» верифікації недержавним співробітником.
